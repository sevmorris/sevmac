Overview

This reference guide documents my setup, tools, and workflows. The tools are open source. The methods apply to many systems, but the configuration applies only to my computer. You must change the configuration to use these tools on your system.

2.1

mrk — What It Does

three-phase bootstrap

The mrk tool is a personal macOS bootstrap system. It automates a clean installation. It manages the shell environment, dotfiles, system preferences, Homebrew packages, application settings, login items, and personal application preferences. The system operates in three independent phases. You can safely run each phase again.

Table 2.1-1. The Three Phases
PhaseCommandWhat It Covers
Phase 1 — Setupmake setupXcode CLT, dotfiles, scripts/bin in ~/bin, macOS defaults, sets Zsh as login shell, installs oh-my-zsh and the configured zsh plugins (zsh-autosuggestions, zsh-syntax-highlighting)
Phase 2 — Homebrewmake brewInstalls Homebrew, runs all packages from the Brewfile with interactive selection for new installs
Phase 3 — Post-Installmake post-installApp configs, browser policies, dev runtimes (openjdk, nvm, pyenv), Barkeep install, preference plist imports, login items

Run all three phases at once:

make all && exec zsh
Two-Repo Design
The mrk system uses two repositories: sevmorris/mrk (public) and sevmorris/mrk-prefs (private). The public repository contains scripts, the Brewfile, and dotfiles. The private repository contains application plists and Application Support files. This design keeps personal data out of the public repository. You can restore the full setup on any machine if both repositories are current.
2.2

New Machine Setup

full install walkthrough
Step 1

Clone and Install

Clone mrk over HTTPS. Do not use SSH because it is not set up yet on a new machine. Run the full installation.

git clone https://github.com/sevmorris/mrk.git ~/mrk
make -C ~/mrk all
exec zsh

This command runs all three phases. It also builds the TUI binaries. The command exec zsh reloads the shell to load dotfiles and ~/bin.

What gets linked (Phase 1):

FilePurpose
.aliasesShell aliases
.gitconfigGit configuration
.hushloginSuppresses "Last login" terminal message
.zprofileZsh login shell profile
.zshenvZsh environment variables
.zshrcZsh interactive shell config
Makefilemrk commands available from ~/

The system copies replaced files to ~/.mrk/backups/ as backups. The system creates a rollback script for macOS defaults at ~/.mrk/defaults-rollback.sh.

What Phase 3 does:

  • Topgrade: The system links assets/topgrade.toml to ~/.config/topgrade.toml.
  • Browsers: The system applies Safari defaults, managed policies for Chrome and Brave, and Helium defaults. The system asks before it opens browser extension install URLs. Non-interactive runs skip this step.
  • Dev runtimes: The system symlinks the Homebrew openjdk into /Library/Java/JavaVirtualMachines/. The system installs nvm into ~/.nvm. The system installs the pyenv Python version specified in .python-version.
  • App defaults: The system applies defaults write settings for Audio Hijack, Fission, AlDente, and all Rogue Amoeba applications.
  • Barkeep: The system downloads and installs Barkeep from the latest GitHub release.
  • Git remote: The system changes the mrk origin from HTTPS to SSH after GitHub SSH authentication succeeds.
  • Preferences auto-pull: The system clones mrk-prefs into ~/.mrk/preferences/ if SSH is authenticated.
  • Plist imports: The system imports preferences for 14 applications. This step is non-destructive. It skips any application with existing preferences.
  • App Support restore: The system restores Loopback and SoundSource configuration files. This step is non-destructive.
  • Config trees: The system restores the Calibre configuration directory (~/Library/Preferences/calibre) when the application is unconfigured.
  • Login items: The system registers AlDente, BetterSnapTool, Chrono Plus, Dropbox, Ice, Raycast, SoundSource, and Stats.
Step 2

Set Up SSH

You need a working SSH key to pull preferences and to push mrk changes. There are two ways to get one, and which one you use depends on where this machine comes from.

Caution — Moving From Another Mac? Do Not Generate a New Key
If you made an archive with snapshot-keys on the old machine, restore it instead. A new key leaves your GPG keys and your Developer ID signing identity behind, and the signing key cannot be re-created. Restore first, then continue at Step 3.

Moving from another Mac — restore the archive.

make -C ~/mrk restore-keys ARGS=<archive>   # ~/.ssh, ~/.gnupg, signing identities
ssh-add -l                                 # SSH keys
gpg --list-secret-keys                     # GPG secret keys
security find-identity -v -p codesigning   # signing identities
ssh -T git@github.com
# Expected: Hi sevmorris! You've successfully authenticated...

An existing ~/.ssh or ~/.gnupg is moved aside with a timestamp before the restore, never overwritten in place. Use ARGS="-l <archive>" to list the contents first.

Starting fresh — generate a new key.

ssh-keygen -t ed25519 -C "your-email@example.com"
cat ~/.ssh/id_ed25519.pub | pbcopy
# Add to: github.com → Settings → SSH and GPG keys → New SSH key
ssh -T git@github.com
# Expected: Hi sevmorris! You've successfully authenticated...
Step 3

Pull Preferences

If the installation did not automatically pull preferences (because SSH was not set up), pull them now. Then, run Phase 3 again.

pull-prefs
make post-install   # Re-run to import plists
Step 4

Restore Repositories

Clone the repositories that the manifest names. snapshot-prefs writes the manifest to ~/.mrk/preferences/repos.tsv, and Step 3 brings it to this machine, so run this after pull-prefs.

make -C ~/mrk restore-repos ARGS=-n   # Show what would be cloned
make -C ~/mrk restore-repos           # Clone them

A repository that is already on disk is skipped. A bare repository is listed but never cloned, because it shares a working tree with another repository and a plain clone puts the files in the wrong place. Set one up by hand, then use decloud for it.

Step 5

Verify the Installation

status          # Open the mrk-status TUI health dashboard (in ~/bin after exec zsh)
make status     # Plain-text installation status report
make doctor     # Check ~/bin is on PATH; pass ARGS=--fix to add ~/bin to .zshrc
2.3

Brewfile Management

keeping packages current
2.3.1

sync — Scan and Update

Scan installed packages, compare them to the Brewfile, and add missing packages.

sync                  # Interactive — opens mrk-picker TUI to select packages
sync -n               # Dry run — show what would be added, make no changes
sync -c               # Auto-commit the Brewfile after updating
sync -p               # Prune — remove Brewfile entries for packages no longer installed

How sync works:

  1. The tool reads the Brewfile to find packages that are already tracked.
  2. The tool runs brew leaves --installed-on-request and brew list --cask to find installed packages.
  3. The tool finds packages that are installed but not in the Brewfile.
  4. The tool opens the mrk-picker TUI. Press Space to select, Enter to confirm, or q to quit.
  5. The tool prompts you with gum to choose a Brewfile section for each formula.
  6. The tool automatically assigns casks to the existing cask section.
  7. The tool inserts each entry alphabetically into its section.
Note — mrk-picker Binary
The mrk-picker binary lives at bin/mrk-picker (gitignored, platform-specific). If it's missing, rebuild with make picker.
Note — Ignore List
To keep a package installed but never have sync suggest it, list it in ~/.mrk/sync-ignore — one formula or cask name per line, # comments allowed. The file is not created automatically.
2.4

App Preferences

snapshot-prefs / pull-prefs

The private sevmorris/mrk-prefs repository stores application preferences. The system clones this repository to ~/.mrk/preferences/. After you configure an application, capture and push the changes.

2.4.1

snapshot-prefs — Capture and Push

Export all managed application preferences and push them to the private repository.

snapshot-prefs

How it works:

  1. The tool exports the preference plist for each managed application with defaults export. It has a 15-second timeout for each application and converts files to XML.
  2. The tool copies managed Application Support files (Loopback, SoundSource) and configuration trees (Calibre).
  3. The tool scans all captured files for secrets (API keys, tokens, and private keys).
  4. The tool commits all changes to ~/.mrk/preferences/ with a timestamped message.
  5. The tool pushes the commits to sevmorris/mrk-prefs on GitHub.

This command is idempotent. It reports "No changes to push" if nothing changed. The tool skips applications if their export fails or times out. It shows a warning and lists skipped applications at the end of the run.

Caution — Secret Scan
If the scan finds a possible secret in a staged file, the push stops for confirmation. The push aborts immediately in non-interactive runs. You must review the flagged file before you try again.
Warning — mrk-prefs Holds Key Material
The config/calibre/plugins/DeACSM/account/ directory holds real key material. The system keeps it deliberately: it cannot be regenerated without a re-authorization. The secret scan does not report it, because its XML element names match none of the scanner's patterns — so nothing else will tell you it is there. The sevmorris/mrk-prefs repository must stay private for this reason.
2.4.2

pull-prefs — Clone or Update

Clone or update preferences from the private repository.

pull-prefs

The tool clones mrk-prefs into ~/.mrk/preferences/ if the directory does not exist. It performs a fast-forward pull if the directory does exist. The make post-install command calls this automatically when SSH is authenticated and ~/.mrk/preferences/ does not exist. It does not pull updates into an existing clone.

Login Items

sync-login-items

The sync-login-items tool compares current system login items to the list in scripts/post-install and synchronizes them.

sync-login-items          # Interactive — select items to add or remove
sync-login-items -n       # Dry run — show what would change, make no changes
sync-login-items -c       # Auto-commit changes after updating

How it works:

  1. The tool reads the current system login items with AppleScript.
  2. The tool parses add_login_item calls from scripts/post-install.
  3. The tool finds the differences between the system and the tracked list.
  4. The tool opens an interactive selector (gum) for you to choose items to add or remove.
  5. The tool updates scripts/post-install with the new items.
  6. The tool also updates docs/manual.md with the new list.

2.6

Migration Checklist

before moving to a new machine

Do these steps on the old machine before you transfer data.

Caution — Step 1 Is the One With No Second Chance
Your Developer ID signing key is generated once and cannot be re-derived. Apple will issue a new certificate, but the private key that pairs with the old one is gone, and every released app loses its signing continuity. The same applies to your SSH and GPG private keys: mrk-prefs never carries them, and no other step in this checklist captures them. Run snapshot-keys before you wipe anything.
Pre-Migration

Checklist — Old Machine

1. Bundle the key material

make -C ~/mrk snapshot-keys

This command writes ~/.ssh, ~/.gnupg and your code-signing identities to one passphrase-encrypted archive. Write the archive to an encrypted external disk. Store the passphrase in your password manager. Use ARGS=-n first to see what the archive holds.

The command asks for two passphrases when you keep the signing identities: one for the archive, and one that macOS sets on the exported .p12. Store both. The second one is necessary to import the identities, even from a good archive.

2. Sync the Brewfile

sync -c

This command captures packages that you installed since the last sync. It commits the updated Brewfile.

3. Snapshot app preferences

snapshot-prefs

This command exports and pushes all application preference plists and Application Support files. Make sure that "Pushed to git@github.com:sevmorris/mrk-prefs.git" shows in the output. If the secret scan finds a secret, the push stops for confirmation. You must resolve the problem before you continue.

4. Push any pending mrk changes

cd ~/mrk
git status
git push

5. Run a Magic Backup Machine backup

Open Magic Backup Machine. Run a full backup to the local and external destinations. This backup copies Logic Pro projects, audio presets, browser profiles, and other data that mrk does not manage.

6. Verify SSH authentication

ssh -T git@github.com
# Expected: Hi sevmorris! You've successfully authenticated...

7. Note anything not covered

  • App Store applications — You must manually install these again from your Purchases.
  • Software licenses — Export licenses from your license manager.
  • VPN configurations, certificates, and system settings that defaults write does not capture.
  • notarytool credentials — A keychain profile has no export, so no backup can carry one. On the new machine, create each profile again with xcrun notarytool store-credentials <name> --apple-id <id> --team-id <team>. Omit --password and notarytool asks for it, which keeps the app-specific password out of your shell history.
On the New Machine
Do the New Machine Setup procedure (Section 2.2). Then, restore data from Magic Backup Machine after you install the applications.

Status & Diagnostics

mrk-status / state files

Run the status command to open the interactive mrk-status health dashboard. Run make status to print a plain-text report. The dashboard shows eight checks with ✓/⚠/✗ indicators, and a ninth Backups panel only when a backup exists. Press f to suggest a fix. The mrk-status tool prompts for confirmation before it runs the fix. Press r to refresh the dashboard.

  • Dotfiles — The tool shows the files symlinked into ~/ and missing files.
  • Tools — The tool shows live and broken symlinks in ~/bin.
  • macOS Defaults — The tool shows if defaults are applied (it looks for the rollback script).
  • Security Hardening — The tool shows if security hardening is applied.
  • Backups — Shown only when backups exist: how many, where, and the most recent. This is a report, not a health check — it can neither fail nor be fixed — so with nothing to report the panel is omitted rather than shown empty.
  • Shell — The tool shows the current login shell. It must be Zsh.
  • PATH — The tool shows if ~/bin is on the PATH.
  • Homebrew — The tool shows the installed version.
  • Brewfile packages — The tool shows if each formula and cask is installed or missing.

Note — What the Backups Are, and Why There Is No Fix
When make setup links a dotfile, it examines the destination first. If a file is there and it is not a symlink — a .zshrc you wrote before mrk existed — setup moves it into ~/.mrk/backups/<timestamp>/ instead of deleting it. If the destination is already the correct symlink, setup skips the file and makes no backup.

The directory therefore holds the machine's pre-mrk dotfiles. The repository is the source of truth for mrk's own dotfiles; the backup is the only copy of what they replaced.

On a clean installation the directory does not exist at all. It is created only at the moment setup displaces a file, so its absence means setup never found one. Running make install again does not create it, because setup skips destinations that are already correct symlinks. Nothing restores these files either — make uninstall does not read them, and neither does any other script. They are an inert archive to copy from by hand. This is why the Backups panel offers no fix: nothing is broken.

Run this command to undo macOS defaults that mrk applied:

bash ~/.mrk/defaults-rollback.sh

Barkeep — Overview

homebrew manager

The Barkeep application is a native macOS application. It visually manages your Homebrew Brewfile. It works with mrk and defaults to ~/mrk/Brewfile. But, it can work with any Brewfile.

The application has a three-pane interface. You can browse entries, view package details (such as man pages, tldr examples, and reverse dependencies), and run Homebrew commands. You do not need to use the terminal.

Table 3.1-1. Barkeep Feature Overview
FeatureDescription
Brewfile viewPackages are in groups by section with an inline search. Select an entry to see its description, version, dependencies, examples, man page, and other data.
ConsoleThe console shows streaming brew command output. The application clears the console at the start of each command.
ActionsYou can install, uninstall, reinstall, upgrade, tap, untap, add to the Brewfile, or remove from the Brewfile. You can select multiple items for a batch upgrade, uninstall, and adopt.
Installed viewA sidebar tab shows all installed brew packages. This includes packages that the Brewfile does not track. The toolbar shows untracked and outdated package counts.
Bundle actionsThe toolbar stack menu and the Bundle menu have these actions: Install Missing (⌘I, runs brew bundle install), Add Untracked to Brewfile, Cleanup Untracked, and Scan for Migratable Apps.
Auto-reloadThe application watches the Brewfile. It reloads automatically when the file changes on the disk.
Updates & helpAn update checker runs at launch. You can also select Barkeep → Check for Updates. Press ⌘? to open a Help window.
Brewfile pickerThe default is ~/mrk/Brewfile. You can change it with the toolbar folder button or File → Choose Brewfile (⌘O).

3.3

Barkeep — Interface & Usage

three-pane layout

The interface has a three-column layout. The left column lists Brewfile entries in groups by section. Select an entry to show its details in the center column. The right column is the console. It shows streaming output from your brew commands.

3.3.1

Package Actions

Select a package in the left column to see its full details and available actions.

  • Install / Uninstall / Reinstall — This action runs the matching brew command.
  • Upgrade — This action runs brew upgrade <package>. The application shows this option when the package is outdated.
  • Tap / Untap — This action is for tap entries.
  • Adopt — This action adds an installed package to the Brewfile if it is not already tracked.
  • Remove from Brewfile — This action removes the entry from the Brewfile. It does not uninstall the package.
  • Multi-select — Select multiple packages for a batch upgrade, uninstall, or add-to-Brewfile.

The console output streams in real time in the right column.

3.3.2

Changing the Brewfile

The Barkeep application does not have a Settings window. You choose the Brewfile directly.

  • Brewfile path — The default is ~/mrk/Brewfile. Change the path with the folder button in the toolbar, or select File → Choose Brewfile (⌘O).
4.1

Magic Backup Machine — Overview

rsync-based backup & restore

The Magic Backup Machine application is a native macOS application. It backs up and restores application settings, presets, and configuration files. It uses rsync to mirror source directories to a local backup folder (~/.backups by default) and an optional external drive.

This application copies files that mrk does not manage. These files include Logic Pro projects and presets, Audio Unit presets, iZotope RX presets, Audio Hijack sessions, browser profiles, and specific application plists.

4.2

Magic Backup Machine — Installation

download and first launch
4.2.1

Download and Install

Download the DMG from the latest release. Drag it to Applications. Then, clear the quarantine flag.

Download from: sevmorris/magic-backup-machine (private repository) → Releases

Caution — Required Before First Launch
The macOS blocks the application because it is not notarized with Apple. Drag Magic Backup Machine to Applications, and then run this command in Terminal: 
xattr -cr "/Applications/Magic Backup Machine.app"

After installation, you can update from inside the application. Select Help → Check for Updates. This action checks the latest release in the private repository. The application also accepts an --auto-backup launch argument for scheduled backups (Section 4.7).

4.3

First Launch

full disk access

On the first launch, the application checks for Full Disk Access. If it does not have this access, a yellow warning banner shows at the top with three buttons:

  • Test Sources — This action runs the Full Disk Access check again and refreshes source availability. It does not restart the application.
  • Open System Settings — This action opens Privacy & Security → Full Disk Access.
  • Quit & Relaunch — This action restarts the application to apply the new permission.
Warning — Full Disk Access Required
If you do not have Full Disk Access, rsync fails on protected directories in ~/Library. Add the application in System Settings → Privacy & Security → Full Disk Access before you run a backup.
4.4

Backup Mode

mirror source → destination

The backup operation mirrors each source directory to every available destination with this command:

rsync -a --delete --ignore-errors --stats <source>/ <destination>/<source_name>/
  • --delete — This flag makes the backup an exact mirror. The tool removes files from the backup if they are not in the source.
  • --ignore-errors — This flag lets the tool continue if a file has an error.
  • --stats — This flag prints a transfer summary at the end.
  • The tool always excludes .DS_Store files.
  • The tool skips source directories that do not exist (it marks them "skipped" in orange).
  • If successful, the tool writes a last_backup.log file to each destination with the timestamp.

Destinations: The backup operation always writes to the local destination. If you configure an external destination and mount its volume, it writes there too. The application creates both destinations automatically if they do not exist.

The application stores each source directory as a named subdirectory in the destination. For example, ~/Library/Audio/Presets backs up to ~/.backups/Presets/. If you use the dated-snapshots layout (Section 4.7), the application creates a YYYY-MM-DD folder in each destination for each run.

Run confirmation: When you select Run Backup, a confirmation sheet opens. This sheet shows the sources, destinations, and a size estimate. From this sheet, select Dry Run to preview the run. This action uses rsync --dry-run --itemize-changes and shows the number of files to transfer and delete. The application shows a notification when a run completes.

Progress: The left panel shows the status of each item during a run. The statuses are: pending (empty circle), in progress (spinner), success (green checkmark), partial (yellow ⚠), failed (red ✗), or skipped (orange dash). The console output streams in real time in the right panel. The header shows the date and destination of the last successful backup. Click the folder button to show the backup folder in Finder.

4.5

Restore Mode

copy backup → source

The restore operation copies files from the backup to their original source locations with this command:

rsync -au --stats <destination>/<source_name>/ <source_parent>/
  • -u (update) — This flag copies only files that are newer in the backup than on the disk.
  • No --delete flag — The restore operation never removes files from the source.
  • The tool skips items that are not in the backup.

The restore operation reads from one destination at a time. A "Restore from" picker (Local/External) shows when both destinations are available. If a destination becomes unavailable, the application switches to an available destination and shows a message. If you use the dated-snapshots layout, a Snapshot picker lets you choose the backup date to restore.

Note — Switching Modes
Use the mode picker in the header to switch between Backup and Restore. The footer always shows a note about the rsync behavior for the current mode.

4.7

Settings

gear icon → Settings sheet

Select the gear icon in the header to open Settings. The Settings sheet has these options:

  • Source Directories — This section lists all configured sources with labels, paths, and filter summaries. Each entry has an enable/disable toggle, a Filters editor for its include and exclude patterns, and a remove button. Select Add Directory to add a new source.
  • Backup Layout — The Mirror option (default) overwrites backups in place. The Dated snapshots option creates a YYYY-MM-DD folder in each destination for each run.
  • Local Backup Destination — The default is ~/.backups. Select Choose... to change it.
  • External Backup Destination — This destination is not configured by default. It is optional. The application uses it only when the volume is mounted. Select Choose... to set it. Select Clear to remove it.
  • Scheduled Backup — This is an optional daily backup at a specific hour and minute. It installs as a launch agent that opens the application with --auto-backup. Scheduled runs can skip the confirmation sheet. You must have Full Disk Access and the application must be in /Applications. The logs are in ~/Library/Logs/Magic Backup Machine/.
  • Settings File — Select this to export or import the full configuration as a JSON file.
  • Reset to Defaults — Select this to revert all settings to the built-in defaults.

The application saves settings in UserDefaults under io.github.sevmorris.BackupRestore. Run this command to force a reload of built-in defaults after an application update:

defaults delete io.github.sevmorris.BackupRestore BackupSettings
Note — New Source Directories After an Update
When an application update has new default source directories, a settings migration adds them automatically. These new directories are disabled by default. You must enable them in Settings. Or, you can select Reset to Defaults, or run the defaults delete command above, to reset to the shipped defaults.
